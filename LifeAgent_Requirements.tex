% ─── SECTION 1: VISION ────────────────────────────────────────────────────────
\section{Vision \& Purpose}

\textbf{The Life Agent} is a personal AI system designed to act as Mahir's accountability partner, life coach, and data-driven advisor --- available 24/7 via Telegram.

The core insight motivating this system: most habit and productivity tools fail because they are \textit{passive}. The user must remember to open them. The Life Agent is \textit{active} --- it initiates contact, asks questions, notices patterns, and calls out inconsistencies based on real logged history. It cannot be bullshitted.

\textbf{What it replaces:}
\begin{itemize}[noitemsep]
    \item A personal trainer (fitness accountability)
    \item A nutritionist (food tracking and guidance)
    \item A life coach (goal setting, direction, tough conversations)
    \item A financial advisor (spending patterns, savings discipline)
    \item A study partner (CFA prep, books, learning accountability)
    \item A scheduler (time management and life planning)
    \item A journal (longitudinal record of where Mahir has been)
\end{itemize}

\textbf{What it does not replace:}
\begin{itemize}[noitemsep]
    \item Mahir's own will and decision to show up
\end{itemize}

The agent's value compounds over time. After 3 months of logs, it knows patterns the user cannot see himself. After 12 months, it can project where consistent behaviour leads.

% ─── SECTION 2: PHILOSOPHICAL FRAMEWORK ──────────────────────────────────────
\section{Philosophical Framework}

The agent's advice and default reasoning should be grounded in the following frameworks. These are not static --- Mahir may update, add, or remove them over time.

\subsection{Andrew Huberman (Science-Based Optimisation)}
\begin{itemize}[noitemsep]
    \item Morning sunlight exposure within 30--60 minutes of waking
    \item Delay caffeine 90--120 minutes after waking
    \item Prioritise deep sleep (consistent bedtime, no screens before bed)
    \item Fasted morning exercise where possible for alertness
    \item Controlled dopamine management --- avoid cheap dopamine early in the day
    \item Meal timing: avoid large meals close to sleep
\end{itemize}

\subsection{Hamza (Discipline \& Masculinity)}
\begin{itemize}[noitemsep]
    \item No excuses framework --- results are the only measure
    \item Purpose-first living: every action either moves toward the goal or away from it
    \item Consistency over intensity: showing up at 60\% beats not showing up
    \item Social media and entertainment as tools, not defaults
    \item Self-respect through keeping promises to yourself
\end{itemize}

\subsection{General Principles}
\begin{itemize}[noitemsep]
    \item Non-negotiables are sacred --- they are the floor, not the ceiling
    \item Progress tracked in weeks and months, not days
    \item Comparison is only to past self, never others
    \item Discomfort is the signal that growth is happening
\end{itemize}

\textbf{Flow for a typical message (polling mode):}
\begin{enumerate}[noitemsep]
    \item Backend polls Telegram every second for new messages
    \item Message received --- intent classifier runs first (is this a slash command, habit log, or free-form?)
    \item If structured intent (e.g.\ \texttt{/done gym}): handle directly, update DB, reply, done
    \item If free-form: backend assembles tiered context from DB (see Section 6)
    \item Backend calls Claude API with assembled context + user message + tool definitions
    \item If Claude calls \texttt{search\_web}, backend executes Tavily query and returns results to Claude
    \item Claude generates final response (with citations if search was used)
    \item If Claude called \texttt{log\_data} during the conversation, backend writes the structured JSON directly to Supabase --- no text parsing
    \item Backend sends reply to Telegram
\end{enumerate}

% ─── SECTION 5: DATA MODEL ────────────────────────────────────────────────────
\section{Data Model}

\textbf{Design principle: KISS + DRY.} Seven tables cover the entire system. The \texttt{logs} and \texttt{records} tables use a \texttt{type} field and a flexible \texttt{JSONB} column (PostgreSQL binary JSON --- indexed, fast, queryable) to handle all domains without table proliferation. Recommended indexes: \texttt{(user\_id, date)} on \texttt{logs}, \texttt{(user\_id, type, date)} on \texttt{records}, \texttt{(user\_id, timestamp)} on \texttt{conversations}.

\begin{lstlisting}[language=SQL]
-- Core identity, preferences, OAuth tokens, and onboarding state
users (
    id, telegram_user_id, name, timezone,
    wake_time, sleep_target_time,
    tone_preference TEXT,           -- 'hamza' | 'huberman' | 'flexible'
    google_refresh_token TEXT,      -- Google Calendar OAuth
    strava_refresh_token TEXT,      -- Strava OAuth
    onboarding_complete BOOLEAN DEFAULT FALSE,
    created_at
)

-- Goals + non-negotiables unified
-- is_non_negotiable = true means sacred weekly minimum
goals (
    id, user_id, title, description,
    timeframe TEXT,              -- '1yr' | '5yr' | '10yr' | 'ongoing'
    category TEXT,               -- 'health' | 'finance' | 'study' | 'life'
    is_non_negotiable BOOLEAN,
    target_per_week INT,         -- only used when is_non_negotiable = true
    current_streak INT DEFAULT 0,
    longest_streak INT DEFAULT 0,
    active BOOLEAN,
    created_at, updated_at
)

-- All daily captures: habits, mood, food, finance, study, social, reflection
logs (
    id, user_id,
    type TEXT,       -- 'habit' | 'mood' | 'food' | 'finance'
                     --  | 'study' | 'social' | 'reflection'
    date DATE,
    goal_id INT,     -- nullable; used to link habit logs to a specific goal
    data JSON,       -- flexible per type (see examples below)
    notes TEXT,
    created_at
)

-- Semi-permanent personal data and agent-generated summaries
records (
    id, user_id,
    type TEXT,       -- 'blood_test' | 'body_comp' | 'medical'
                     -- | 'dietary' | 'decision' | 'weekly_summary'
                     -- | 'brain_snapshot'
    date DATE,
    data JSON,
    source TEXT,     -- 'lab report' | 'InBody scan' | 'manual' | 'agent'
    file_url TEXT,   -- nullable; Supabase Storage URL for original uploaded file
    notes TEXT,
    created_at
)

-- Upcoming hard dates: CFA exam, travel, deadlines
-- source distinguishes manual entries from Google Calendar imports
events (
    id, user_id, title TEXT,
    date DATE, type TEXT,
    source TEXT DEFAULT 'manual',   -- 'manual' | 'google_calendar'
    notes TEXT
)

-- Extensible life domain configs — agent can create/activate/deactivate via conversation
-- Adding a new tracking area = inserting one row. Zero code changes.
domains (
    id, user_id,
    name TEXT,                   -- 'cold_shower' | 'screen_time' | 'journaling'
    display_name TEXT,           -- shown to Mahir: "Cold Showers"
    active BOOLEAN,
    evening_prompt TEXT,         -- "Did you have a cold shower today?"
    context_decay_days INT,      -- how far back to pull logs for context
    nudge_after_days INT,        -- nullable; days without a log before nudge fires
    system_prompt_snippet TEXT,  -- injected into Claude system prompt when active
    created_at
)

-- Full message history
conversations (
    id, user_id,
    role TEXT,           -- 'user' | 'assistant'
    content TEXT,
    timestamp DATETIME
)
\end{lstlisting}

% ─── SECTION 6: AGENT LOGIC & CONTEXT INJECTION ───────────────────────────────
\section{Agent Logic \& Context Injection}

\subsection{What Gets Injected into Every Claude Call}

Context is assembled in tiers. Each tier has a different decay rate --- how far back data remains useful varies by type. Older data is not discarded; it is compressed into the brain snapshot rather than removed.

\begin{longtable}{>{\bfseries}p{1.5cm} p{4cm} p{4cm} p{4.5cm}}
\toprule
Tier & Content & Decay Rate & Rationale \\
\midrule
1 & Goals, non-negotiables, tone, user profile & Near-zero & Anchors; always relevant \\
\addlinespace
1 & Latest health records (blood test, body comp, medical notes) & Slow (3--6 months) & Biology changes slowly \\
\addlinespace
1 & Latest brain snapshot & Weekly rewrite & Compressed state; replaces raw history \\
\addlinespace
2 & Daily logs: last 14 days, full detail & Fast (14 days) & Daily signal; pattern emerges over weeks \\
\addlinespace
2 & Study logs: weighted by CFA proximity & Event-driven & High weight as exam approaches; resets after \\
\addlinespace
2 & Strava activities + Apple Health metrics: last 14 days & Fast (14 days) & Real workout and sleep data; cross-referenced with mood and energy logs \\
\addlinespace
2 & Google Calendar events: next 14 days & Time-bounded & Pulled nightly; agent knows schedule before check-in \\
\addlinespace
3 & Weekly summaries: last 4, full text & Medium (8 weeks) & Already condensed; useful longer than raw logs \\
\addlinespace
3 & Upcoming events: next 14 days & Time-bounded & Exam dates, travel, deadlines \\
\addlinespace
4 & Older data & Compressed into brain snapshot & Not injected raw; prevents token bloat \\
\bottomrule
\end{longtable}

Tier 1 is cached via Anthropic prompt caching, reducing input token cost by up to 90\% on the largest part of the prompt.

\subsection{Domain-Driven Extensibility}

All tracking domains (fitness, finance, study, etc.) are rows in the \texttt{domains} table, not hardcoded logic. The agent reads active domains at runtime and builds the evening review, context injection, and nudge schedule from them dynamically.

\textbf{What this means in practice:}
\begin{itemize}[noitemsep]
    \item Evening review loops over active domains and asks each one's \texttt{evening\_prompt}
    \item Context injection loops over active domains and pulls the right window of logs per domain
    \item Scheduler checks \texttt{nudge\_after\_days} per domain and fires nudges automatically
    \item System prompt concatenates \texttt{system\_prompt\_snippet} from all active domains
\end{itemize}

\textbf{Agent self-extension:} Mahir can tell the agent to start tracking something new in plain conversation. The agent asks two or three clarifying questions, writes the domain config row, and the new domain is live from that evening's review. No code change, no redeployment.

\textbf{Example:}
\begin{lstlisting}
Mahir:  "I want to start tracking cold showers"
Agent:  "Got it. Just yes/no each evening, or do you want
         to log duration too?"
Mahir:  "Just yes/no. And remind me if I miss 3 days."
Agent:  [inserts row into domains table]
        "Done. I'll ask you about cold showers tonight.
         3-day nudge is set."
\end{lstlisting}

\textbf{Deactivation:} the agent can also deactivate domains --- ``stop tracking cold showers'' sets \texttt{active = false}. History is preserved. The agent can suggest deactivating domains with no logs in 30+ days.

\subsection{Tool Use --- Web Search + DB Writes}

Two tools are defined in every Claude API call. Claude calls them autonomously based on context.

\textbf{Tool 1: \texttt{search\_web}} --- live web retrieval via Tavily. Claude calls this when advice quality benefits from current research or forum discussions.

\begin{lstlisting}
{
  "name": "search_web",
  "description": "Search the live web for current information.
                  Use when advice benefits from recent research,
                  forum discussions, or up-to-date guidance.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "domains": { "type": "array", "items": { "type": "string" } }
    },
    "required": ["query"]
  }
}
\end{lstlisting}

\textbf{Tool 2: \texttt{log\_data}} --- structured DB write. Instead of the backend parsing Claude's text to infer what should be logged (fragile), Claude explicitly calls this tool with structured JSON when it determines something should be recorded. Reliable, unambiguous, impossible to misparse.

\begin{lstlisting}
{
  "name": "log_data",
  "description": "Write a structured log entry to the database.
                  Call this whenever the user reports something
                  that should be recorded: habit completion, mood,
                  food, spend, study session, or any active domain.",
  "input_schema": {
    "type": "object",
    "properties": {
      "type":    { "type": "string" },
      "date":    { "type": "string", "format": "date" },
      "data":    { "type": "object" },
      "notes":   { "type": "string" }
    },
    "required": ["type", "data"]
  }
}
\end{lstlisting}

Example: Mahir says ``gym done, felt strong, mood 8''. Claude calls \texttt{log\_data} twice --- once for the habit log, once for the mood log --- with clean JSON. Backend writes directly. No text parsing.

For scheduled proactive messages that always need web data, the backend calls Tavily manually before the Claude call and injects results into context.

\subsection{Proactive Intelligence}

The scheduler triggers agent-initiated messages:

\begin{itemize}[noitemsep]
    \item Morning check-in: daily at configured wake time
    \item Evening review: daily at configured evening time (covers gym, food, mood, spend, study)
    \item Gym nudge: no gym log in 72+ hours
    \item Study nudge: no study log in 48+ hours; escalates as CFA exam approaches
    \item Mood check: mood below 6/10 for 5 consecutive days $\rightarrow$ deeper conversation
    \item Sunday weekly summary: auto-generated + brain snapshot rewritten
    \item Monthly meta-review: first Sunday of each month
    \item Relationship nudge: no social log in 10+ days
    \item Financial nudge: spend log missing for 3+ consecutive evenings
    \item Missed review recovery: if evening review was skipped, next morning check-in acknowledges the gap and offers to catch up before moving to today
\end{itemize}
